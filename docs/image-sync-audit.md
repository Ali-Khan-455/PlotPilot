# Image-Sync — rulings

Decisions made while building Image-Sync. The architecture and the user's answers (Q0–Q9, C1–C4) are in `docs/image-sync-plan.md`; this file records the implementation rulings, phase by phase.

## IS-1 — Foundation

| # | Ruling |
|---|---|
| IS-D1 | **Shared derivation.** `plotpilot.final.derive_inputs` (bodies and the D20 target, available before any hook exists) and `derive_outputs` (hook, script, scene lines, and per-chunk lines, available once the `hook_tts` pass exists) are the single source for PlotPilot's final script and metadata. `run_final` uses both in its existing order. `derive_outputs` calls `scene_lines` once for the whole novel and then splits the result by each chunk's scene count. It does **not** run the D20 splice check: `run_final` and `imagesync.source.load_novel` each call it separately. One reordering has no observable effect: scene parsing now happens before `script.txt` is written, and a done chunk always has an ok `scenes` pass. |
| IS-D2 | **Loader.** `plotpilot.prompts.load_prompts(path, heading_re, key, required)` stays backward compatible for v4. Required sections fail closed: a missing heading, or a section without COPY and END markers, raises instead of being skipped. `load_section` returns a raw `## heading` section. `imagesync.spec.load_spec` parses the v3 stages, the locked suffix (the first fenced block after its heading line), the sub-styles (a)–(d) and the colour treatments. Any change to that structure fails closed. It also checks that every `MODULE_TO_COLOR` label exists in the spec, which guards IS-4's later lookup `colors[MODULE_TO_COLOR[genre_color_default]]`. |
| IS-D3 | **Read-only source.** `plotpilot.db` is opened with `mode=ro` through a resolved file URI, and nothing in imagesync writes to it (a test compares the file's checksum before and after). A novel is ready when every chunk is `done`, `derive_outputs` succeeds and the splice check passes. The first unmet condition is named in the error. `database is locked` becomes a clear "busy" error. |
| IS-D4 | **Hash binding.** `novels.plotpilot_source_sha` is copied verbatim from PlotPilot's `novels.source_sha256` and never recomputed here. `script_sha` is sha256(script + NUL + metadata lines), recomputed on every run. A mismatch refuses to run and names the hash that changed. Recovery: when PlotPilot was deliberately rebuilt (for example `plotpilot.db` was deleted and the novel re-planned), delete `imagesync.db` and re-run, because beats built from the old narration can't be reused. |
| IS-D5 | **Style lock.** The operator makes this choice; no model is involved. The suggestion is the dominant drafting module across chunks, mapped with C3 (A→c, B→b, C→a, D→d). On a tie, the module of the earliest tied chunk wins. The lock is a `style_lock` pass with `model` and `chunk_id` NULL, plus Bible version 1 with `chunk_idx` NULL, because it is novel-level. Both rows are written in one transaction by `add_bible_version(pass_fields=…)`. A partial unique index allows one style lock per novel, and a concurrent loser gets a friendly message. The Bible stores letters only: `sub_style` and `genre_color_default` (the dominant module's letter). Spec text is resolved at render time (IS-4). |
| IS-D6 | **Bible versions.** `source_pass_id` is `UNIQUE`, which protects against a replayed accept of the same pass. `chunk_idx` is NULL for novel-level rows. The newest row wins (`ORDER BY id DESC`). |
| IS-D7 | **Spec observations for IS-4 (questions for the user then).** v3 says "Replace the two bracketed fields", but the suffix has **three**: sub-style descriptor, genre colour treatment and aspect ratio. The sub-style bullets read `Name — description`, so IS-4 must decide which part fills `[sub-style descriptor]`. |
| IS-D8 | **C4 — how the model is shown the JSON contracts (blocks IS-2, resolved).** Each stage's user message is that stage's v3 prompt text, unchanged, followed by the appendix's "How the model uses these contracts" override paragraph, followed by that stage's JSON contract block. The override paragraph explicitly says to ignore the markdown format above and to omit any field not in the schema (so the model doesn't re-add `cadence_warning`, `slot` or `manifest_rows`, which C1 already has code recompute). **Fallback, not yet implemented:** if a model's first real Stage 0/1/2 runs mix markdown and JSON despite the override, the fix is a per-stage "format-strip": send the v3 prompt text with its own `Output format:` section removed programmatically at call time and replaced by the override plus the contract. That is a call-time edit to the prompt fragment, never a change to the spec file. Defer until real runs actually show the problem. |

## IS-2 — Stage 0

| # | Ruling |
|---|---|
| IS-D9 | **Stage 0's context, `CONTINUES`, and cadence.** Stage 0 is shown only the previous chunk's last continuity-log entry (one pre-rendered line, labeled with the spec's own `CONTINUITY LOG (append-only)` line), never the whole Bible — omitted entirely for chunk 1 or when the log is empty. `continues` is a yes/no signal only: the model's own text is never trusted or compared; when `has_continuity` allows it, code substitutes the previous chunk's actual last beat's display timecode, matching C1's "code has the final say" pattern. Cadence is computed per beat within a scene group (a group's total duration split evenly across its beats), not as a raw gap between distinct timecodes, and print-only, never a gate. Concurrent Image-Sync runs on the same novel are not guarded beyond the style-lock's unique index — a known, accepted gap, consistent with IS-1's own analogous deferral. |
| IS-D10 | **`Source.hook`.** `imagesync.source.Source` gained a `hook` field (the video's actual opening line, from `plotpilot.final.Outputs.hook`). Chunk 1's Stage 0 input prepends it to the chunk's narration, since PlotPilot's hook lives outside every chunk's own narration body — without it, no beat would ever cover the opening line the finished video actually starts on. |

## IS-3 — Stage 1 (references) and the Visual Bible

| # | Ruling |
|---|---|
| IS-D11 | **Spec-contract edit.** `prompts/image-sync-v3.md`'s Stage 1 output contract spells out a uniform `bible_update` item shape per type (`name`, `tag`, `descriptor`, optional `current_state`), with a Note documenting the per-type default (`clean` / `intact` / `present`) when it's absent. `Spec.regenerate_line` is a new fail-closed field, mirroring `mode_a_line`/`continuity_log_header`: it asserts the literal substring `"regenerate #Name: [reason]"` is present in `STAGE 1`'s own text and returns it verbatim, never typed as a bare literal sent to the model outside of what the spec itself already says. |
| IS-D12 | **`--regenerate`'s mechanism: hide-from-index, not a rewritten instruction.** The tag index (`_tag_index`) omits the target tag entirely; Stage 1's own "already-generated references aren't re-created" rule then makes the model propose what looks like a fresh reference. The reason reaches the model as `spec.regenerate_line` filled via `plotpilot.prompts.fill`, naming the real tag a second time (`regenerate #RealTag: ...`) as an independent way to land on the right entity. The response's postcondition is relaxed to match reality: the model may legitimately re-propose other recurring elements too, so code (`_match_regenerate_target`) picks the one entry matching by tag or name, discards the rest, and overwrites its tag/category to the target's real ones — code has the final say, the same pattern C1 established for `slot`/`cadence_warning`. |
| IS-D13 | **The composed delta and `replace_tags` are recorded explicitly, in the pass's own `note`, never inferred.** A pass's `note` is `{"delta": ..., "replace_tags": [...]}`. A fresh Stage 1 pass always has `replace_tags: []`; a regenerate's `replace_tags` is the previous pending state's tags plus the target's tag only if the target is already merged into the Bible — this is what lets a regenerate of a still-pending reference take the normal append path later, while a regenerate of an already-approved one correctly replaces in place. `_pending_refs_pass` is the single canonical read of "what's pending right now": the latest ok `refs` pass, specifically — `None` only if *that* pass is bound to a `bible_versions` row. A looser "any unbound pass" reading would resurrect an older, already-superseded pass once a later regenerate's pass is approved (the original pre-regenerate pass is itself never bound). `_compose` preserves a still-pending target's existing index in `new_references` rather than always appending, since `merge` assigns slots strictly in that array's order — always-append would silently reassign every other pending entry's slot whenever a still-pending reference was regenerated. |
| IS-D14 | **The locked style suffix is resolved in full (retires IS-D7).** `bible._render_suffix(spec, bible, module)` fills all three brackets: the sub-style's name only (not its description, to avoid biasing the image model toward copyrighted reference titles) from the locked `sub_style`; the genre color treatment for the *current chunk's* own drafting module (not the Bible's locked default); the locked aspect ratio. It asserts no `[` remains afterward, failing closed if a future spec edit adds a fourth bracket. |
| IS-D15 | **One row per entity; global tag uniqueness.** A transliterated alias is not a second row — `name` holds the original form, `tag` holds the Latin/CamelCase form. `check_no_collision` (ordinary Stage 1 path) and `merge`'s own defensive re-check (regenerate/edited-file path) both compare tags `_norm`-insensitively across every category, not just within one. |
| IS-D16 | **The Bible mirror renders the genre-color label and the sub-style name, not the stored letters.** `bible.render` resolves `config.MODULE_TO_COLOR[genre_color_default]` for the label (the Bible only ever stores the bare module letter) and `spec.sub_styles[sub_style].split(" — ")[0]` for the sub-style's name, shown as `(c) Fantasy adventure manhwa` — matching the CLI's own style-lock suggestion text. `render` and `approve_refs` both take `spec` for this reason. |
| IS-D17 | **The continuation loop.** Once the style is locked, `main` runs `ready` → Stage 0 → `beats`/`refs_pending` → Stage 1, stopping only at the `refs_pending` operator gate or the end of available work — the same "continue past a satisfied gate" shape `plotpilot.pipeline.run_novel` already uses. `--approve-refs`, `--regenerate` and `--revise-beat` are mutually exclusive (checked before the style-lock gate, so the refusal fires even pre-lock) and each prints its own "ignored; the style isn't locked yet" note when given before a lock exists. |
| IS-D18 | **`reference_generated` has no `False` path.** `merge` stamps it `True` for every entry it appends; the field name suggests a separate operator confirmation of Flow generation, but in this design it's synonymous with "merged into the Bible". `refs.txt` is rebuilt from the database-canonical delta on every `run_stage1`/`run_regenerate` invocation and must never be edited directly — an operator's changes belong in the pending JSON file instead, which `--approve-refs` re-validates and merges. |

## IS-4 — Stage 2, the manifest, and the Bible continuity gate

| # | Ruling |
|---|---|
| IS-D19 | **Spec edits.** `genre_override` in the Stage 2 batch output contract is narrowed from a free-text label to `"A" \| "B" \| "C" \| "D" \| null`, with a Note that code resolves the letter via `config.MODULE_TO_COLOR` — never a model-written label. A new `## BIBLE UPDATE (end-of-Stage-2 continuity call)` section, placed after `## STAGE 2` and before `## FAILURE HANDLING`, carries the continuity call's own prompt text; `Spec.continuity_prompt` loads it via `load_prompts` with a custom `heading_re` (never `load_section`, which would leak the `**COPY EVERYTHING BELOW**`/`**END OF...**` marker lines into the model's own input). A new line in STAGE 2's own "Batching" paragraph — `Spec.stage2_context_label`, fail-closed like `regenerate_line` — tells the model that a previous batch's last 3 beats, shown for shot-cadence context, are marked `PREVIOUS BATCH (context only, no prompt needed)` and must not be re-emitted as new prompts; without it, `validate_stage2`'s own beat-count check (IS-D22) would fail on essentially every multi-batch chunk. |
| IS-D20 | **`attempt()`'s `post_validate` hook is append-only correct; re-fetching a verdict from the database is not.** `attempt(..., post_validate=None)` is called only after a shape-valid parse; its return becomes the stored verdict at the same `db.add_pass` call that inserts the pass — never a later update to an already-inserted row. `attempt()` still returns only the parsed value, never the verdict: a caller that needs to know whether `post_validate` fired recomputes the same condition itself from that returned value. Re-fetching the verdict via `db.latest_pass`/`db.ok_passes` would be wrong regardless, since both filter `verdict IS NULL` — a pass whose `post_validate` fired is invisible to them by design (they only ever return *done* passes). |
| IS-D21 | **The QA-retry scheme uses two distinct verdicts, not one.** A batch's first-attempt response that fails QA (`check_refs` and/or `check_shot_cadence`) is stored with verdict `"QA_RETRIED"` — a durable record, never read back for control flow. The retry response's own `post_validate` is a *different* closure: it stores `"QA_FAILED"` only if `check_refs` still fails on the retry — a cadence-only failure on the retry stores `None`, so `db.ok_passes`/`db.latest_pass` correctly treat that retry as the batch's one canonical done pass. `check_refs` failing after the retry is fatal (the whole batch is refused, no file written); `check_shot_cadence` alone is always accepted, printed as a warning. `check_wide_under_9_16` never gates a retry at all — v3 allows a 9:16 wide shot for an explicit landscape, a judgment call code can't make from a `shot_type` string, so it's warn-only, printed unconditionally after acceptance. |
| IS-D22 | **Stage 2's output is validated against the batch's own beat identity, not just its shape.** `compose.validate_stage2(obj, batch)` requires `len(obj["prompts"]) == len(batch)` and each item's (`#`-stripped) `timecode` to equal `batch[i].timecode + batch[i].suffix`, both as `ParseError` (retried once, then failed clearly). This is what makes v3's own "one beat = exactly one image" rule an enforced invariant rather than an assumption, and what makes `manifest.csv`'s row-order-is-beat-order contract (§9/Q9, recorded in IS-1) actually true — IS-5's `--check-images` can rely on it. `manifest.csv`'s timecode column always comes from the stored beat identity, never the model's own `timecode` field — the same "code has the final say" pattern as `slot`/`cadence_warning`/regenerate's tag overwrite. |
| IS-D23 | **Resume is keyed to each pass's own stored range, never `config.BATCH_SIZE`-derived math.** Each `stage2` pass's `note` carries `{"start", "count", "batch_index", "tail"}` — the exact beat range and batch number decided once, when that batch was created, from whatever `config.BATCH_SIZE` was *then*. `_batch_progress` reads the latest ok `stage2` pass's own note for the next start/index; a later `config.BATCH_SIZE` edit can size the *next* batch differently but can never reshuffle or reinterpret a batch already stored. The stored `tail` is the batch's own last **8** shot types (not 3, not 6): `check_shot_cadence`'s periodic-wide-shot rule needs to look back exactly that far in the worst case (a wide shot 8 positions before a batch boundary, with the crossing beat just past it) to correctly attribute a gap to the batch whose beat actually crosses the 7-beat threshold, rather than re-flagging a gap the *previous* batch's own check already covered. |
| IS-D24 | **`run_regenerate` refuses once any `stage2` pass exists for the chunk.** Dropping the pre-Stage-2 `batching` status (nothing ever needed to read it — resume is entirely pass-counting) silently removed the documented cutoff for `--regenerate`: an operator could otherwise ask to regenerate a reference's appearance after its Stage 2 images already exist, which this phase has no mechanism to propagate into already-composed prompts. The guard is a direct precondition check (`db.ok_passes(conn, chunk_id, ["stage2"])` non-empty) naming the chunk and pointing at IS-5's revision path, checked before any model call. |
| IS-D25 | **Every relevant call rewrites every batch file, the pending continuity file, and the manifest — not just the one just written.** `_write_all_batch_files` rebuilds every batch's `.txt` file from every ok `stage2` pass (deduplicated to the latest pass per `batch_index`, guarding the benign race case IS-1's own concurrent-run deferral already accepts), and is called from `run_stage2`, `run_bible_update`, and the CLI's own `bible_pending` branch. `_write_continuity_pending_if_missing` and `_rewrite_manifest` get the same treatment. This closes the crash window between a pass's DB insert and its file writes: a plain rerun at any status before `done` self-heals every artifact, matching `refs.txt`/`bibles/*.md`'s existing precedent from IS-3. |
| IS-D26 | **Continuity state reaches a later chunk's Stage 2 call through the Bible entry itself, not a separate data section.** `bible.merge_continuity(bible, entries, chunk_idx)` has a dual effect: it appends one rendered log line (`[chunk N \| beat M-SS] #Tag from → to reason`) *and* updates the matching tag's own row's `current_state` to the delta's `to` value (last entry wins when a delta touches one tag twice). Because `run_stage2`'s own message always sends the full Bible entries for every ref named in the batch's beats (via `bible._entries`'s render-style shape, which includes `current_state` — never `_tag_index`'s slimmer form), a later chunk's Stage 2 call automatically sees the newest state with no separate continuity-log section needed. This is also why `bible.merge`'s `replace_tags` branch (IS-3, used by `--regenerate`) was corrected to stop overwriting `current_state`: a regenerate only fixes a reference's *appearance*, never its story-state, and the old code silently reset `current_state` back to Stage 1's bare default on every regenerate of an already-approved tag — undoing whatever the continuity log had most recently set, since the regenerate prompt never even shows the model the current `current_state` to preserve it. |
| IS-D27 | **The continuation loop's termination guard is a progress check, not a beat-count-derived cap.** The loop's own outer bound, `OUTER_LOOP_CAP = 64`, is a coarse, fixed backstop against an unrelated bug class (`run_stage0`/`run_stage1` somehow cycling status without ever gating or failing) — it needs no beat-count math, since a correct run only ever needs a handful of status transitions plus one iteration per Stage 2 batch. The actual guard against a stalled `run_stage2` is an explicit `before, _, _ = _batch_progress(...)` / `after, _, _ = _batch_progress(...)` comparison around the call, inside the `refs_approved` branch: if a call returns success without storing a batch, the loop fails immediately, on the very first non-progressing call, naming the exact beat where the stall happened. An earlier design computed the cap from `len(current_beats(...))`, which is `None` until a `"beats"` pass exists — crashing on every fresh chunk, since every chunk starts at `ready`. Known, accepted edge case: a chunk needing more than roughly 61 batches (~1,830 beats at `BATCH_SIZE = 30`) would hit `OUTER_LOOP_CAP` even on a fully correct run, since each successful batch still costs one outer-loop iteration; recoverable by a plain rerun, which resumes exactly where it stopped per `_batch_progress`. |
| IS-D28 | **`validate_continuity` checks tag and beat identity, not narration support.** `bible.validate_continuity` requires `element` to `_norm`-resolve to an existing Bible tag and `beat` to be one of the chunk's own beats' display timecodes (both `#`/`@`-stripped first). It does **not** independently check that the named `element` actually appears in that specific beat's own narration — v3's own prompt text already forbids inventing an unsupported state change, but the validator doesn't enforce it, matching `check_refs`'s own similarly-scoped "not in the beat" deferral (recorded as out of scope, not silently assumed handled). |
